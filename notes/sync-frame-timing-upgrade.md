npc_sync>=0.2.7 adds an invalid_intervals property to flag sections that contain incorrect duplicate data on all lines due to memory aliasing by the original writer. Intervals are typically 1 or 1.5s but can be up to ~10 s. Immediately after the interval the data return to being correct and can be used for inference (however multiple invalid intervals can occur). we need to try as best we can to recreate the events on each line within these intervals using other sources, including:
## stim files / npc_stim
contain frame display intervals that represent the length of each psychopy loop that can be used to recreate vsyncs. also has opto frame onset times (in various different formats), and lick frames. data is recorded on another daq with an unsynced clock, but that shouldn't matter over short intervals.
## ephys data / npc_ephys
usually records the photodiode on an analog input channel. beware that sessions that toggled the b/w diode square on every frame induced flicker (see notes in npc_sync.) barcodes are also recorded on each probe independently, so if a majority of probes agree that a barcode started/ended during an invalid interval it's timing could be recreated. sound onsets can sometimes be derived from the NI-DAQ analog inputs: the speaker signal (ch 1, used by npc_samstim) or the stimulus microphone (ch 3 per npc_ephys `get_pxi_nidaq_data` docstring; confirm per rig/date). 
## video metadata/npc_mvr
metadata json records dropped frame indices. more-recent videos contain frame index as a barcode in the corner of the image.

# notes
- the process of finding frame times in npc_sync was already relying on info from stim files and making assumptions about where they live. I'd prefer to remove this rather than add new data srouces: npc_sync should be for providing line info and maybe doing the splitting by blocks; npc_sessions.Session is for pulling together data from different sources for a single session and ultimately the place where correct times are needed, so perhaps it should be responsible for computing them. this may have major consequences for npc_stim/npc_samstim/npc_mvr though, which have npc_sync as a dependency but will never have npc_sessions, so please evaluate. the alternative is something creates "fixed" files and every other library uses them without modification to their code. the downside to this is we don't have permissions to replace the original files in S3, but npc_lims could just point to the scratch bucket.  
- there are some tolerances in the current npc_sync frame time processing code (eg 1 off in len(vsyncs) - len(stim frames)) that should be revisited: our current understanding of the system is almost certainly incorrect in places. we need to be as strict as possible: a persistent offset of 1 frame (16.66 ms) is unacceptable for neural data. reject sessions that don't make sense, then find plausible explanations and address them if possible.
